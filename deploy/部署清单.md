当前在跑的容器：

| 容器 | 内存 |
|---|---|
| `minio` | 102 MB |
| `WeKnora-postgres` | 94 MB |
| `colorai-nginx` | ~6 MB |
| `nginx-container` | ~6 MB |
| `WeKnora-redis` | 4 MB |

> ℹ️ `WeKnora-neo4j` 与 `mysql8.0` 是 **`Exited`** 状态。它们的 restart 策略分别是
> `always` / `unless-stopped`，但 **`docker stop` 会覆盖重启策略** → **不会自己回来抢内存**
> （除非重启 docker daemon 或手工 `docker start`）。

**为什么仍然要小心：** 要新增的 `agent` 容器是内存大户 —— 它要装 `langchain` +
`langchain-community` + `langgraph` 全家桶，常驻内存 300~600MB；**构建阶段的 `pip install`
峰值可能 0.5~1GB**。可用 845MB 跑得动，**但因为没有 swap，一旦超了就是硬 OOM**。

**后果（按严重度）：**
1. `docker build` 的 `pip install` 阶段被 OOM killer 干掉（表现是构建中途莫名失败）。
2. 容器一起来就 OOM，**而且 Linux 的 OOM killer 不保证只杀新容器** ——
   有可能把 `minio` 或 `WeKnora-postgres` 杀掉，**波及你现有的服务**。

**先选一条路再往下走：**

| 方案 | 代价 | 说明 |
|---|---|---|
| **A. 加 2GB swap**（当前推荐） | 免费，性能略降 | 磁盘 `/` 有 8.8G 空闲，够用。`fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile`；写进 `/etc/fstab` 才是永久的，想撤销就 `swapoff /swapfile && rm /swapfile` |
| **B. 升配到 4GB** | 花钱，可能需重启 | 最干净。1.6GB 同时跑 minio + PG + Redis + 本项目的 agent，本来就超配 |
| **C. 继续停着不用的栈** | 免费 | `WeKnora-*` 那组如果暂时不用就保持停止；`mysql8.0` 也不用起（Go 连的是外部 `39.106.186.3`） |
| **D. agent 部署到别处** | 架构变复杂 | Go 后端留在本机，agent 放另一台机器，`AGENT_URL` 指过去 |
| **E. 分两步走**（可与 A 叠加） | 多一次操作 | 先 `docker-compose build` 只构建镜像、确认构建过了，再 `docker-compose up -d` 启动。构建与启动分开，出问题好定位 |

> 未验证：以上是基于「实测可用内存 845MB、无 swap」的推断，不是跑出来的结论。
> **构建还没实际跑过** —— 这是唯一还没跨过的坎。
> **真正的验证是第一次 `docker build`** —— 见 §5。
>
> ✅ **2026-09-28 起有了规避手段**：走 **§1.2 的离线构建**（本机交叉编译 + 预下 wheel），
> 服务器侧只剩 `COPY`，峰值内存比在线构建低一个数量级 —— 上面这个阻断项基本被绕开了。
> 只剩「拉 `python:3.11-slim` 基础镜像（~45MB）」这一项还需要网络。
> 不过**首次构建仍建议按方案 A 加 2GB swap** 兜底。

### 1.2 离线构建产物（**推荐**，2026-09-28 新增）

`upload_backend.py` 只传「基础文件」。**把编译/装依赖这两件重活挪回本机**要靠第二个脚本：

```bash
cd /d/GoLang/colorAI

# 看清单（不编译、不下载、不联网）
<py> deploy/pack_offline.py --dry-run

# 全流程：下 wheel → 交叉编译 → 校验 → 打包 → 上传 → 远端校验
<py> deploy/pack_offline.py --download-wheels

# 之后只改了业务代码时，wheel 与二进制都能复用：
<py> deploy/pack_offline.py
```

`<py>` = `C:/Users/魏正想/.workbuddy-ai/binaries/python/envs/default/Scripts/python.exe`

它**只传这 5 类**，不碰 `upload_backend.py` 的地盘（职责不重叠，可以各自单独重跑）：

| 产物 | 说明 |
|---|---|
| `go-backend/colorai-backend-linux` | 本机交叉编译的 linux/amd64 **静态**二进制（12.5 MB） |
| `go-backend/agent/wheels/*.whl` | 预下载的 linux wheel 全集（**69 个 / 50.5 MB**） |
| `go-backend/Dockerfile.offline` | 无 Go 构建阶段，只 `COPY` 二进制 |
| `go-backend/agent/Dockerfile.offline` | 无 gcc、不连 PyPI，`--no-index --find-links` 离线装 |
| `docker-compose.offline.yml` | 覆盖层，**只覆盖 `build` 一节** |

**实测（2026-09-28）：**

```
✓ 依赖树完整，可以离线安装          ← Linux 标记重解析
✓ colorai-backend-linux  12.5 MB  [linux/amd64 ELF]
→ 上传 colorai-offline.tar.gz（54.3 MB）   100%
远端校验：
  ✓ docker-compose.offline.yml / Dockerfile.offline ×2 / colorai-backend-linux 13M
  ✓ go-backend/agent/wheels/  69 个 / 51M
  ✓ 二进制 7f 45 4c 46 02 00 3e 00   （ELF 64-bit, EM_X86_64）
  ✓ Dockerfile.offline 里有 chmod +x
  ✓ compose 叠加解析 → agent / go-backend
```

> 🔴 **两个坑**（细节写在 `pack_offline.py` 文件头和 `Dockerfile.offline` 注释里）：
> 1. **`pip download` 在 Windows 上按「Windows 环境标记」求值** → `sys_platform != "win32"`
>    的 Linux 专属依赖被**静默跳过**。实测漏掉 `uvloop`（`uvicorn[standard]` 的 extra），
>    直到服务器上 `pip install --no-index` 才炸。→ 必须带 `--platform` 等参数，
>    且下载完**必须**跑 `pack_offline.py --check-wheels`（硬编码 Linux 标记，是唯一权威校验）。
>    ⚠️ `pip install --dry-run --target ... --python-version 3.11` **不能**当权威 ——
>    实测它同样按宿主 `sys_platform` 求值，输出里也没有 `uvloop`，是同一个盲点换了个命令。
> 2. **tar 上传把权限统一规范化成 0644** → Go 二进制传上去不可执行。
>    所以 `Dockerfile.offline` 里那行 `RUN chmod +x` **删不得**（远端校验会断言它存在）。

### 3.2 `go-backend/agent/.env`

| 键 | 当前值 | 处理 | 原因 |
|----|--------|------|------|
| `PG_HOST` | `118.31.10.161` | **不改** | 已被 compose 覆盖成 `host.docker.internal` |
| `PG_SSLMODE` | `disable` | **不改** ✅ | PG 就在本机容器里，同机通信用 `disable` 是对的 |
| `CORRECTION_API_URL` | `https://api.ququan.net/...` | **不改** | 已与 `app/config.py` 默认值统一。但**仍未跟接口提供方确认过** |

> `Settings()` 直接抛 `extra_forbidden`，**整个 agent 服务起不来**。
> 要加配置必须先在 `app/config.py` 的 `Settings` 里加同名字段。
> （对照：`os.environ` 里的无关变量**不会**触发，只有 `.env` 文件里的键会被查。）

## 5. 起后端

**先选一条构建路径：**

| 路径 | 命令 | 服务器要做什么 | 内存开销 |
|---|---|---|---|
| **A. 在线构建** | `docker-compose up -d --build` | 拉 `golang:1.25-alpine`(329MB) + `go mod download` + 编译；拉 `python:3.11-slim` + `apt-get install gcc` + 联网 `pip install` langchain 全家桶 | **峰值 0.5~1GB** ⚠️ |
| **B. 离线构建**（推荐，见 §1.2） | `docker-compose -f docker-compose.yml -f docker-compose.offline.yml up -d --build` | 只 `COPY`：二进制 + wheel 直接落进镜像 | 几乎可忽略 |

> 路径 B 的前提是**已跑过 `deploy/pack_offline.py`**（把二进制与 wheel 传上去）。
> 它把编译/装依赖挪回本机，正是为了绕开文首那个内存阻断项。
> ⚠️ **必须叠加两个 `-f`** —— `offline.yml` 只覆盖 `build` 一节，
> 单独用会丢掉 `env_file` / `networks` / `healthcheck` / `extra_hosts`。

```bash
cd /home/www/project/colorAI

# 路径 A（在线构建）
docker-compose up -d --build

# 路径 B（离线构建）—— 推荐
docker-compose -f docker-compose.yml -f docker-compose.offline.yml up -d --build
```

**预期与节奏：**

- 会先创建网络 `colorai-net`（固定名，后面 nginx 要接的就是它）。
- **路径 A** 第一次构建慢，**慢的是 agent 的 `pip install`**（langchain + langgraph 全家桶，
  已配清华源）。Go 侧有 `GOPROXY=goproxy.cn`，十几秒编完。
- **路径 B** 两个镜像都只有 `COPY` + 一个 `pip install --no-index`（不编译、不联网），
  但仍要**联网拉基础镜像** `python:3.11-slim`（~45MB）与 `alpine:3.20`（~3MB）。
- 最终 `docker-compose ps` 应是两个容器都 Up，`colorai-agent` 显示 `(healthy)`。

> ⚠️ **路径 A 在内存紧张时有风险** —— 见文首的阻断项。

## 8. 给 colorAI 起独立的 Nginx 容器

### 为什么是「独立容器」而不是塞进 blog 的容器

用户只有一个域名 `wzx.glaty.cn`，已被 blog 占用（80 端口）。**blog 前端也调 `/api`** →
两个站共用 80 必然抢 `location /api/`（要么改前端 baseURL 重新构建，要么抢走 blog 的 /api）。

→ 给 colorAI 单开 **8080**：**换 `listen` 端口 = 换 server 块 = `/api` 天然隔离，
前端代码零改动**（它写死的 `/api` 在 8080 上照样落到我们这个块）。

加端口必须重建容器（端口不能热加），于是有两条路：

| | ❌ 重建 blog 的 `nginx-container` | ✅ 新建独立 `colorai-nginx`（**已采用**） |
|---|---|---|
| blog 停机 | 断 2~3 秒 | **零停机** |
| 以后改 colorAI 的 nginx | 每次都要再冒一次 blog 的风险 | **完全不影响 blog** |
| 重建命令 | 必须把 blog 的挂载/网络一条不漏复现 | 与 blog 无关 |
| 回滚 | stop+rename 后 rename 回来 | `docker rm -f colorai-nginx` 一行 |
| 隔离 | 共用挂载与权限域 | conf 目录独立、内容**只读**挂载 |
| 代价 | —— | 多一个 nginx 进程（实测 ~6MB） |

### 实测的 blog nginx 现状（**我们不动它**，列出来是为了对照）

| 项 | 值 |
|---|---|
| 镜像 | `nginx:1.27-alpine` |
| 启动方式 | **`docker run`**，没有 compose 标签 |
| 网络 | 只接了 `blog-net`（172.20.0.1） |
| 端口 | **只有 80**（`-p 80:80`），没有 443 |
| 挂载 | `/root/nginx/conf.d` → `/etc/nginx/conf.d`（rw）<br>`/root/nginx/blog` → `/usr/share/nginx/html/blog`（rw） |
| 重启策略 | `unless-stopped` |
| 现有站点 | `server_name wzx.glaty.cn`，`root /usr/share/nginx/html/blog` |
| **基线**（任何操作后都应一致） | `blog首页 200` / `blog后台 301` / 挂载 2 条 / 网络 `blog-net` |

> ℹ️ `blog API` 那条**现在就是坏的，别算到我们头上** —— `blog-app` 容器实测
> **`Exited (2)` 已两个月**。静态页正常不代表 API 正常。

### 接入：一条命令

前置：§7 的 dist 已推到 `/root/nginx/blog/colorai/`。

```bash
# 本机执行。脚本会：建 conf 目录 → 传 conf → 校验 → 起容器 → 自动验收
python deploy/nginx_up.py            # 先只读探测，看计划命令
python deploy/nginx_up.py --apply    # 真正创建
```

它做的事等价于：

```bash
mkdir -p /root/nginx/conf.d-colorai
cp deploy/nginx/colorai.conf /root/nginx/conf.d-colorai/colorai.conf

docker run -d --name colorai-nginx \
  --restart unless-stopped \
  -p 8080:80 \
  -v /root/nginx/conf.d-colorai:/etc/nginx/conf.d:ro \
  -v /root/nginx/blog/colorai:/usr/share/nginx/html/colorai:ro \
  --network colorai-net \
  nginx:1.27-alpine
```

容器内 `listen 80`，宿主暴露成 **8080**。以后要加 HTTPS 只需给**这个**容器加
`-p 8443:443` —— 重建它**不影响 blog**。

**常用命令：**

```bash
python deploy/nginx_up.py --verify    # 验收
python deploy/nginx_up.py --reload    # 改了 conf 之后热加载
python deploy/nginx_up.py --down      # 删掉 colorai-nginx（blog 不受影响）
python deploy/nginx_up.py --blog-rebuild   # 需要动 blog 容器时，现场推导等价命令
```

> ✅ **2026-09-24 实测结果**：容器 `Up` / `0.0.0.0:8080->80` / 首页 200 /
> `manifest.webmanifest` 200 / `/assets/index-CEAp0EjS.js` 200 / `nginx -t` ok /
> **blog 首页 200、后台 301（与基线一致，零影响）** / `/api/health` 502（后端未起，预期）。

> 🔴 **还必须去云控制台安全组放行 8080/tcp。** 服务器本机 `curl 127.0.0.1:8080` 通
> **不等于**外网通 —— 不放行的话外面访问会超时。

### 附：真要动 blog 容器时（安全网，正常部署用不到）

> ✅ **正常部署 colorAI 完全不需要这一段** —— 我们的 nginx 是独立的 `colorai-nginx`。
> 这段只在**你要改 blog 自己**时用（例如给 blog 上 HTTPS）。

**别手抄重建命令** —— 用脚本从现场 `docker inspect` 推导，避免漏参数：

```bash
python deploy/nginx_up.py --blog-rebuild    # 打印等价的重建命令
```

它当前推导出来的是：

```bash
docker run -d --name nginx-container \
  --restart unless-stopped \
  -p 80:80 \
  -v /root/nginx/blog:/usr/share/nginx/html/blog \
  -v /root/nginx/conf.d:/etc/nginx/conf.d \
  --network blog-net \
  nginx:1.27-alpine
```

标准流程（stop + rename，**不 rm**，随时能退回）：

```bash
# 1) 先备份配置目录
cp -r /root/nginx /root/nginx.bak-$(date +%Y%m%d-%H%M%S)

# 2) 停 + 改名（保留旧的，出问题能立刻退回去）
docker stop nginx-container
docker rename nginx-container nginx-container.old

# 3) 用上面推导出的命令重建。要加 -p 443:443（上 HTTPS）就加在这一行。
#    带 -v / --network / --restart 的行**必须原样保留** —— 漏了会怎样见下面的表。
docker run -d --name nginx-container \
  --restart unless-stopped \
  -p 80:80 \
  -p 443:443 \
  -v /root/nginx/blog:/usr/share/nginx/html/blog \
  -v /root/nginx/conf.d:/etc/nginx/conf.d \
  --network blog-net \
  nginx:1.27-alpine

# 4) 按需接本项目网络（可选；colorAI 有自己的容器，通常不需要）
docker network connect colorai-net nginx-container
```

### 附：改 colorAI 自己的 nginx（**不影响 blog**）

改了 `deploy/nginx/colorai.conf` 之后：

```bash
python deploy/nginx_up.py --reload    # 先 nginx -t 校验，过了才 reload
```

要加端口（例如上 HTTPS 的 `-p 8443:443`）：改 `deploy/nginx_up.py` 的 `container_cmd()`
后再 `--apply` 重建 —— **只影响 colorai-nginx，blog 一个字节都不动**。

### 附：`docker run` 的语义（对任何容器都成立）

> ⚠️ **`docker run` 是「重新创建一个容器」，不是「往原容器上加东西」。**
> 挂载和网络**不会累积、也不会继承** —— 新容器的挂载列表**完全等于**你这次命令行里写的那些。
> 所以「加一个新挂载会不会让原来的 blog 失效」的答案是：
> **不会 —— 前提是你把原来那两个挂载原样再写一遍。** 真正会出事的不是「多写」，
> 而是「漏写」。下面这三样，**少任何一个都会坏，但坏得不一样**：
>
> | 参数 | 漏了会怎样 | 症状好不好发现 |
> |---|---|---|
> | `-v /root/nginx/blog:/usr/share/nginx/html/blog` | blog 前端与后台**全 404** | ✅ 一眼可见 |
> | `-v /root/nginx/conf.d:/etc/nginx/conf.d` | 所有站点配置消失，只剩 nginx 默认欢迎页 | ✅ 一眼可见 |
> | `--network blog-net` | **静态页正常，但 `/api/` 与 `/files/` 挂**（它们要解析 `blog-app` / `minio`） | 🔴 **部分失败，最难查** |
>
> 最后一条是最阴的：`blog-nginx.conf` 里有
> `proxy_pass http://blog-app:8083`（`/api/`）和 `proxy_pass http://minio:9000/`（`/files/`），
> 都靠 `blog-net` 的服务名解析。**丢了网络，首页照样 200，只有接口挂** ——
> 很容易误判成"后端坏了"。
>
> **好消息：数据永远不会丢。** `/root/nginx/blog` 是**宿主上的目录**，容器只是把它挂进来。
> 重建容器、甚至用完全错误的命令重建，都动不到宿主文件。
> 加上上面用的是「**stop + rename，不 rm**」，旧容器还在，随时能退回去。

**重建前先记基线，重建后逐条比对**（这是判断「有没有漏参数」最快的方法）：

```bash
# 重建前（在服务器上执行），把输出存下来
curl -s -o /dev/null -w 'blog首页   %{http_code}\n' -H 'Host: wzx.glaty.cn' http://127.0.0.1/
curl -s -o /dev/null -w 'blog后台   %{http_code}\n' -H 'Host: wzx.glaty.cn' http://127.0.0.1/admin
curl -s -o /dev/null -w 'blog API   %{http_code}\n' -H 'Host: wzx.glaty.cn' http://127.0.0.1/api/
docker inspect nginx-container --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}'
docker inspect nginx-container --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
```

> **2026-09-24 实测基线**（重建后应完全一致）：
> `blog首页 200`、`blog后台 301`、挂载 2 条、网络 `blog-net`。
>
> ℹ️ `blog API` 那条**现在就是坏的，别算到重建头上** —— `blog-app` 容器实测
> **`Exited (2)` 已两个月**（镜像 `blog-blog-app:latest` 还在）。静态页正常不代表 API 正常。

**回滚**（如果新容器起不来）：

```bash
docker rm -f nginx-container
docker rename nginx-container.old nginx-container
docker start nginx-container
```

> ⚠️ `docker run` 那一步会**短暂中断 `wzx.glaty.cn`**（约 2~3 秒）—— 这正是我们不把
> colorAI 塞进 blog 容器的原因：`colorai-nginx` 是独立的，改它 blog 完全不停机。

### 还没有 HTTPS

实测 **443 没有任何监听**，也没有 certbot。后果：

- 站点只能跑在 `http://`。
- **Service Worker 只在 HTTPS 下注册** → PWA 离线缓存静默失效（页面本身不受影响）。

补 HTTPS 时注意：**certbot 追加的 443 server 块不会继承** `client_max_body_size` /
`location /api/` / `location /` —— 它只复制 `server_name` 和 `root`。
**必须在 443 块里再写一遍**，否则会出现「http 能传图、https 传图 413」这种极难查的问题。

## 附：设计决策速查（免得日后自己推翻自己）

| 决策 | 原因 |
|------|------|
| 前端**不**打包成镜像 | 产物就是静态文件，没有构建期逻辑；打镜像只是多一层要维护的东西 |
| 前端由**独立的 `colorai-nginx` 容器**托管，而**不**塞进 blog 的容器 | 只有一个域名且已被 blog 占 80，**blog 前端也调 `/api`** → 共用 80 必然抢 `location /api/`。换 `listen` 端口（8080）= 换 server 块 = 天然隔离 + **前端零改动**。独立容器还带来：blog **零停机**、conf/内容目录全独立且内容**只读**、以后改 colorAI 的 nginx 不影响 blog、回滚一行命令。代价仅多 6MB 内存 |
| dist 放 `/root/nginx/blog/colorai/`（而不是 `/var/www/colorai`） | 独立容器可以只读挂载这一个子目录，隔离反而更紧；不用动 blog 的挂载与权限 |
| `AGENT_URL` / `REDIS_ADDR` / `PG_HOST` 放 `environment:` 而**不**放 `.env` | 容器里必须用服务名 / 本机网关；但 `.env` 本地开发也在用，写死这些值会让本地连不上 `127.0.0.1` |
| `3001` 只绑 `127.0.0.1` | 仅供服务器上 curl 排障。写成 `3001:3001` 会监听 `0.0.0.0`，任何人都能绕过 nginx 直打后端 |
| agent **不**映射端口 | 只有 go-backend 需要访问它，走内网即可。暴露出去没用还扩大攻击面 |
| `.dockerignore` **不**整体排除 `agent/` | `main.go` 里 `import "colorai-backend/agent"` 就是 `agent/manager.go`（Go 包），和 Python 项目**共用目录名**。整体排除会直接编译失败 |
| agent 的 CMD 用 `python -m app.main` 而**不是** `uvicorn --port 8000` | 端口硬编码在 Dockerfile 里，与 `settings.AGENT_PORT` 一旦不一致，容器仍监听 8000 而 Go 指向别处，排查成本极高。走 `__main__` 分支让配置说话 |
| Go 在容器里**不会**拉起 Agent | `manager.go` 有三重存在性检查（`agent/` 目录、`.venv`、`.env`），容器里都不存在 → 只打一行「跳过启动」日志。Agent 由编排独立提供 |
| 重建命令一律**从 `docker inspect` 现场推导**，不手抄 | 漏一个挂载就把 blog 弄挂。`nginx_up.py --blog-rebuild` 干的就是这件事 |
