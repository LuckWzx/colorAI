# 智能体接口演进设计（异步任务与交互入口）

> 目标：为「AI 生图、3D 全景、点击取色」等后续能力落地，定义对话接口数据结构的演进方案。
> 范围：只定义协议、接口与状态模型的演进，**不含生图 / 3D 模型服务的选型与实现**。
> 依据：2026-10-08 接口现状评审（链路：前端 → Go 代理 → Python Agent → MySQL 持久化）。

---

## 一、现状回顾（评审结论）

### 1.1 现有数据结构（三层一致）

**请求**（`ColorAI/src/types` → `ChatMessage`）：

```json
{
  "sessionId": "session-0a1b2c3d4e5f6789",
  "messageId": "msg-0a1b2c3d4e5f6789",
  "messages": [
    { "role": "user", "content": "请校色", "feature": "correct", "images": ["https://..."] }
  ],
  "model": "deepseek-flash"
}
```

**响应**（`message` 信封，Agent 构造、Go 透传）：

```json
{
  "id": "msg-...", "role": "assistant",
  "type": "text | correct | pick | compare | convert | phone",
  "content": "...", "metadata": {}, "createdAt": 1694678400000
}
```

**持久化**（`chat_messages` 表）：`msg_type + content + payload(TEXT, JSON)`，payload 存 metadata。

### 1.2 时序约束（评审实测）

| 环节 | 现状 | 出处 |
|------|------|------|
| 前端整体超时 | 90s（`AbortSignal.timeout(90000)`） | `ColorAI/src/services/chatService.ts` |
| Go → Agent 超时 | 60s（`http.Client{Timeout: 60s}`） | `go-backend/service/chat_service.go` |
| 校色实测耗时 | 约 11~15s（同步链路可行） | `chatService.ts` 注释 / 校色设计文档 |

### 1.3 已确认的三个缺口

1. **同步模型撑不住长任务**：AI 生图 30s~3min、3D 重建 1~10min，60s 超时直接中断。
2. **消息不可更新**：`chat_messages` 只有追加（`AppendMessages`），无更新能力；任务完成无法把"生成中"改成结果。
3. **交互事件无处安放**：点击取色需要坐标（x/y），而 `ChatMessage` 只有 `content / feature / images`——且这类确定性计算不该走 LLM 链路。

### 1.4 结论（评审定调）

**外框（消息信封、metadata 开放结构、payload JSON、feature 短路机制）足以承载未来能力，不需要推倒重来。**
真正要补的只有两块：**① 异步任务范式（任务态消息 + 状态查询 + 消息更新）**；**② 轻交互专用入口（点选取色绕开对话链路）**。

## 三、核心设计一：异步任务范式（P0）

### 3.1 任务态消息模型

长任务提交后，Go **立即**返回一条「任务态消息」占位（不等 Agent 完成）：

```json
{
  "success": true,
  "message": {
    "id": "msg-0a1b2c3d4e5f6789",
    "role": "assistant",
    "type": "task",
    "content": "正在为您生成装修效果图，预计需要 1~2 分钟…",
    "metadata": {
      "taskId": "msg-0a1b2c3d4e5f6789",
      "taskType": "render",
      "status": "pending",
      "progress": null
    },
    "createdAt": 1694678400000
  }
}
```

**关键约定（决策 1）：任务完成后「原地更新」这条消息，`type` 替换为最终类型。**

```json
{
  "id": "msg-0a1b2c3d4e5f6789",
  "role": "assistant",
  "type": "render",
  "content": "装修效果图已生成（3 张方案）",
  "metadata": {
    "success": true,
    "images": [
      { "url": "https://.../render_0.jpg", "style": "现代简约" },
      { "url": "https://.../render_1.jpg", "style": "奶油风" }
    ],
    "sourceImage": "https://.../user_room.jpg",
    "params": { "roomType": "living-room" }
  },
  "createdAt": 1694678400000
}
```

理由：
- 用户视角：一条任务 = 一条消息（进度 → 结果），不刷屏；
- 历史加载统一：刷新后已完成任务就是普通结果卡片，前端渲染逻辑零分裂——**`type: "task"` 只出现在未完成时**。

失败时保持 `type: "task"`（供前端渲染失败态 + 重试按钮）：

```json
{
  "type": "task",
  "content": "效果图生成失败",
  "metadata": {
    "taskId": "msg-0a1b2c3d4e5f6789",
    "taskType": "render",
    "status": "failed",
    "error": "生成服务超时，请重试",
    "retryable": true
  }
}
```

**决策 2：`taskId` 与消息 `id` 相同**（同一 ID 空间）。理由：一个任务天然对应一条消息，省掉一层映射与一张关联表；`GET /api/tasks/:id` 即 `WHERE chat_messages.id = ?`。

### 3.2 状态机

```
        ┌─────────┐   任务开始执行   ┌─────────┐   成功：type 替换为 taskType   ┌────────┐
提交 ──► │ pending │ ─────────────► │ running │ ─────────────────────────────► │ 完成态  │
        └─────────┘                  └─────────┘                                └────────┘
                                        │  失败 / 超时
                                        ▼
                                    ┌────────┐   用户重试（前端重发 /api/chat）
                                    │ failed │ ──────────────────────────────► 新任务
                                    └────────┘
```

- `done` 不显式保存：正文表明"完成态"即 `type` 已非 `task`，查询时由 `type != 'task'` 判定。
- `failed` 保持 `type='task'`，`metadata.status='failed'`，`retryable` 指示可否重试。
- 超时清理：`pending/running` 超过任务上限（可配 `AGENT_ASYNC_TIMEOUT`，默认 600s）标记为 `failed`（由 Go 定时任务或惰性检测执行）。

### 3.3 状态查询：轮询（决策 3）

**v1 采用轮询，不做 SSE。** 理由：

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **轮询** `GET /api/tasks/:id` | 实现简单、可断线恢复、Nginx 零配置 | 实时性略差（1~2s 间隔足够） | ✅ v1 |
| SSE / WebSocket | 实时推送 | 连接管理、Nginx buffering、断线恢复复杂 | 挂起（`messageId` 字段注释已为它预留） |

**接口定义：**

```
GET /api/tasks/:taskId      （需登录；仅任务归属者可查）
```

```json
{
  "success": true,
  "task": {
    "taskId": "msg-0a1b2c3d4e5f6789",
    "status": "running",
    "progress": 0.4,
    "message": { "…最新消息快照（字段同 /api/chat 的 message）…" }
  }
}
```

- `status`：`pending | running | done | failed`；
- `message` 始终返回最新快照——**done 时它已是最终结果卡片**，前端直接替换本地消息即可；
- 前端轮询间隔建议 1.5~2s，`done / failed` 后停止；页面刷新后按会话消息中的 `type == 'task'` 自动恢复轮询。

### 3.4 消息更新：服务端内部能力（决策 4）

**不对外暴露 PATCH 消息接口。** 任务态更新只由服务端在任务完成后执行：

```
UPDATE chat_messages
SET msg_type = <最终类型>, content = <最终文案>, payload = <最终 metadata>, task_status = ''
WHERE id = <taskId>
```

理由：对外写接口会引入越权与状态篡改面；前端只需要"读状态"，写操作用户侧本来就有语义入口（重发 /api/chat）。

### 3.5 数据库改动

`chat_messages` 增加一列（一次性 ALTER，建表脚本同步维护）：

```sql
ALTER TABLE chat_messages
  ADD COLUMN task_status VARCHAR(16) NOT NULL DEFAULT ''
  COMMENT '任务状态：空=非任务/已完成；pending/running/failed=进行中/失败';
```

用途：① 僵尸任务清理查询（`WHERE task_status IN ('pending','running')`）；② 运维排查。
应用层不依赖它渲染（渲染判定看 `msg_type='task'`），加列是小成本换运维能力。

### 3.6 Go → Agent 调用策略（决策 5）

**v1：Go 侧分流，Agent 无感知。**

| 任务类型 | 链路 | 超时 |
|----------|------|------|
| 短任务（correct 等 ≤ 30s） | 保持现有同步 | 60s 不变 |
| 长任务（render / panorama） | Go 建任务消息 → 立即返回前端 → goroutine 调 Agent | 放宽至 `AGENT_ASYNC_TIMEOUT`（默认 600s） |

- 异步判定（v1）：**feature 白名单配置**（如 `ASYNC_FEATURES=render,panorama`），快捷按钮路径确定性强、零歧义；
- 自由对话命中的长任务 v1 暂走同步+放宽超时，v2 随 Agent job 化统一；
- **局限（必须记录）**：goroutine 持有长连接，Go 服务重启会中断任务 → 消息卡在 `running` → 由超时清理标 `failed`，用户重试。可接受性：v1 部署为单实例低频重启。

**v2 演进（挂起，不做进 v1）**：Agent 侧 job 化（提交即返回 jobId，Go 轮询 Agent 状态），支撑服务重启恢复与 10min+ 任务。

## 四、核心设计二：点击取色入口（P1）

### 4.1 定位澄清：两种「取色」是两回事

| 名称 | 语义 | 交互形态 | 现状 |
|------|------|---------|------|
| 主色调提取（现有 `type: "pick"` 卡片） | 提取整图主导色 + 占比 | 消息卡片（走对话链路） | 视觉服务未交付，工具未注册 |
| **点击采样（本节）** | 点击图上某点 → 该点颜色 | 弹层/气泡（即时交互） | 协议未定义 |

两者**不复用同一卡片与 type**，避免交互形态混淆。

### 4.2 首选方案：前端本地采样（决策 6）

点击取色是确定性像素计算，**首选前端实现，零延迟、零后端成本**：

1. `canvas.drawImage` 绘原图 → `getImageData(x, y)` 取该点 RGB；
2. 复用 `ColorAI/src/utils/colorConverter.ts` 换算 HEX / RGB / HSL / CMYK / Lab / HSV；
3. 弹层展示色值，支持一键复制（与现有取色卡片视觉一致）。

坐标语义：**一律换算到原图自然像素坐标**（前端负责缩放/拖动换算）。
全景图注意：屏幕点击 → 纹理坐标需要经过**投影反变换**（由全景查看器组件负责），属于前端实现细节，协议层不涉及。

### 4.3 备选方案：服务端接口（口径强一致时）

若要求色值口径与后端（Colour-Science）严格一致，追加轻量接口（不经过 Agent / LLM）：

```
POST /api/color/pick        （需登录）
```

```json
{ "imageUrl": "https://.../photo.jpg", "x": 512, "y": 300 }
```

```json
{
  "success": true,
  "color": { "hex": "#FF6B35", "rgb": { "r": 255, "g": 107, "b": 53 }, "…FullColorValues…" }
}
```

- `x / y`：原图自然像素坐标；超界返回 400；
- 响应 `color` 结构复用 `FullColorValues`（现有契约，不新创）；
- 图片可取任何已落库 URL（自有 OSS），服务端下载后采样。

## 五、核心设计三：资源引用与产出图落库规范（P1）

### 5.1 问题

现有图片 URL 来源混杂：`f3.ququan.net/temp/check/`（校色服务托管，**疑似临时链接**）、自有 OSS（用户上传图）。校色卡片目前依赖 `SmartImage` 的"过期兜底"兜住——体验有损。

### 5.2 规范（决策 7）

1. **凡"产出型图片"必须转存自有 OSS 后入库**：生图、全景图、以及**建议**的校色结果图转存（校色结果转存可独立决策，不阻塞本设计）；
2. **消息间引用不依赖裸 URL**：迭代修改类请求（"把这张图再改改"）在请求侧以 `messageId + imageKey` 引用，服务端解析为实际 URL：

```json
{
  "role": "user", "content": "把沙发换成蓝色",
  "references": [ { "messageId": "msg-0a1b...", "imageKey": "images.0" } ]
}
```

`references` 为**可选扩展字段**（`ChatMessage` 新增），v1 不强制使用；生图迭代开发时启用。

3. 远期若需要资产化（配额、审计、清理），再引入 `asset` 表（`assetId + url + kind + expiresAt`）——**预留字段语义，不提前建表**。

## 六、扩展流程固化：新增一个 type / 能力的标准步骤（P2）

生图/全景落地时按此顺序执行（延续项目"未实现不注册、防幻觉"纪律）：

1. **契约先行**：在 `ColorAI/src/API.md` 定义新 `type` 名、metadata schema、完整示例——**未写契约不写代码**；
2. **Agent 侧**：工具实现 → `get_all_tools()` 注册 → `TOOL_TYPE_MAPPING` 映射 type →（图片参数为 URL 时）`FEATURE_TOOL_MAPPING` 登记；
3. **Go 侧**：透传零改动；长任务类型加入 `ASYNC_FEATURES` 配置；
4. **前端侧**：`types/index.ts` 定义 metadata 类型 → 新增卡片组件 → 历史兼容（老消息无新字段时降级为文本，不得白屏）；
5. **回归**：老会话加载测试（含分页历史）、失败态测试、刷新恢复测试。

**metadata schema 建模建议**：Agent 侧为每个卡片类型补 pydantic 模型（`Agent/app/models/`），替代现在"靠 normalize 函数对齐"的做法；`correct` 可作第一个示范。

**历史富上下文（挂起事项）**：现在前端每次回传完整历史（仅 `role + content`），LLM 看不到历史消息的图片引用。迭代修改任务（生图系列）开发时，需要把生成结果的引用摘要带进历史，否则"刚才那张图"在 LLM 眼里不存在。

## 七、接口变更汇总

| 接口 | 现状 | 本次设计 | 优先级 |
|------|------|---------|--------|
| `POST /api/chat` | 纯同步 | 长任务分流：先返回 `type=task` 占位 | P0 |
| `GET /api/tasks/:taskId` | 无 | 新增：任务状态轮询 | P0 |
| `chat_messages` 表 | 无任务字段 | 加列 `task_status` + 消息 UPDATE 能力 | P0 |
| `POST /api/color/pick` | 无 | 新增：点选取色（备选，前端本地采样优先） | P1 |
| `ChatMessage.references` | 无 | 新增可选字段（迭代修改时启用） | P1 |
| 消息 PATCH 接口 | 无 | **决策：不做**（服务端内部更新） | — |
| SSE / WebSocket | 无 | **决策：v1 不做**（轮询先行，字段已预留） | 挂起 |

**无需改动**：`message` 信封结构、`metadata: any` 开放结构、`payload` TEXT 存 JSON、`feature` 短路机制、请求侧 images 的 base64→落盘→URL 约定。

## 九、待确认事项

1. **生图 / 3D 模型服务的提供方与接口形态**（搭档自建 or 第三方 API；同步 or 异步；耗时上限）——直接影响 `ASYNC_FEATURES` 范围与超时配置；
2. **校色结果是否转存自有 OSS**——成本换"永不失效"体验，可独立决策；
3. **全景图格式**（equirectangular / cubemap）与前端查看器选型（Three.js photo-sphere 或等价方案）；
4. **点选取色的精度要求**——若前端本地换算可接受，4.3 的服务端接口可不实现。
